# ADR-013: Deterministic repair / re-validation design

- **Status:** Accepted
- **Date:** 2026-09-04

## Context

Candidate repairs must not be presented as "corrected payments" until they pass deterministic
validation. LLM output is never authoritative.

## Decision

- Terminology: outputs are **REPAIR_CANDIDATE** until deterministic validation succeeds, then
  **VALIDATED_CANDIDATE**; otherwise **REVIEW_REQUIRED** or **UNRESOLVED**.
- Flow: original -> analysis -> proposed field changes -> reconstruct candidate XML -> XSD
  validation -> CloudNova rule validation.
- XML reconstruction is **controlled** (parsed tree + structured changes), never generated by
  an LLM. Unrelated fields are preserved; the original tree is never mutated (deep copy).
- Every candidate re-validates against the bundled XSD **and** the rules engine before being
  marked VALIDATED.
- A structured diff model records path, before/after, source, and status.

## Consequences

- No unvalidated candidate is ever labelled "corrected".
- Deterministic, reproducible repair.
- Frontend diff UI can be built later on the backend diff data.
